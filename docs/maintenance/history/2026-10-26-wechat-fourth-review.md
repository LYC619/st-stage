## 1. W9 / P1：新增测试的回调类型阻断类型检查

位置：`st-extension/src/apps/wechat/wechat.test.ts:760-769,882-895`。

`pnpm exec tsc --noEmit --incremental false` 稳定执行结果为退出 1，两个 TS2322：

- 第 769 行：Promise 的 resolve 只接受 `Record<string, unknown> | undefined` 及对应 PromiseLike，却被赋给声明为可接收任意 unknown 的 `resolveAliceVars`。
- 第 895 行：宿主消息回调需要一个 string 参数，被赋给声明为无参数函数的 `callbacks.onMsg`。

需要按实际 AppHost 契约声明 deferred resolver 与消息回调，并在调用测试回调时提供必要参数。Vitest 转译执行通过不会证明 TypeScript 类型检查通过。该问题位于本轮新增测试，是明确的门禁失败；本轮未据此声称已执行或观察到 Next 构建失败。

## 2. W4 / P2：同一聊天的并行读取仍能用旧结果覆盖新结果

位置：`st-extension/src/apps/wechat/wechat-app.ts:468-486`。

新的挂载/会话代次与键检查已经修复跨角色及卸载分支，但同一会话内每次刷新共享这些标识。初始化、消息与变量结算事件可以发起重叠的异步 `getVariables` 读取；只要未切会话，旧请求晚返回仍可提交。

复现：同一 Alice 会话的初始读取挂起，再触发变量更新读取。先让新读取返回 mood=96，页面正确显示 96；随后旧读取返回 mood=82，页面回退为 82。宿主接口明确允许 Promise 返回，测试不能只使用立即返回的数值。

应增加独立的刷新序号或取消旧读取，确保旧快照不覆盖较新快照。不要用切会话代次替代刷新序号，以免正常状态更新无故取消当前 LLM 发送。

## 3. W1c / P2：评估期间新接管的外部字段仍被本地增量修改

位置：`st-extension/src/apps/wechat/wechat-app.ts:767-784`。

`hasExternalMood/hasExternalInterest` 在 await 状态评估前计算，提交时只检查会话有效性，没有重新确认字段是否已经由外部接管。同一会话内的变量更新可以在等待期间改变 `externalFields`。

复现：初始只映射外部 money，心情/好感仍独立；发消息后将本地状态评估挂起。随后变量事件带来真实 mood=82、interest=35，并标为外部字段。最后返回本地 +0.4，保存值变为 82.4/35.4，外部字段标记仍为 true。外部原值并未改变。

应在提交增量时重新读取当前字段所有权，或给状态快照增加修订检查。已在评估开始前存在的外部字段当前确实受保护，本条不否定那部分修复。

## 4. W1c / P2：红包仍直接扣减外部钱包快照

位置：`st-extension/src/apps/wechat/wechat-app.ts:673-681`。

下一天的生活费分支已检查外部金钱字段，但红包路径仍无条件 `activeConv.state.money -= amt`，没有写回外部源，也没有撤销外部来源标记。

复现：宿主固定返回 money=1000 且映射成功；点击 20 元红包后，本地保存 980，`externalFields.money` 仍为 true。界面继续宣称该金额来自外部源；下次读取又会恢复 1000。

需保持外部快照只读，将模拟红包账目另存，或另行定义真实写回契约。不能在未更新宿主的情况下把修改后的缓存当成外部余额。

## 5. W1a / P2：无效优先候选遮住同角色的合法别名

位置：`st-extension/src/apps/wechat/bridge.ts:82-85,132-136`。

`findCandidate` 先返回第一个非 null 键，再在外层尝试类型转换。高优先级别名有值但无法转换时，会跳过当前池剩余合法别名并进入根对象池。

独立复现输入 `{ Alice: { mood: 'calm', happiness: [82, 'note'] }, mood: 12 }`，对 Alice 的 `readExternalCharacterState` 返回外部 mood=12，而当前角色明确存在、且已在支持列表中的 happiness=82 被跳过。删除无效文本 mood 后即得到 82。空的 location 遮住合法 place 有相同机制。

应在每个别名上完成解包及类型转换，找到第一个有效值才停止；当前角色池的所有有效候选应先于根池。无需扩大任意字段猜测，仅需正确处理代码已声明支持的别名。
