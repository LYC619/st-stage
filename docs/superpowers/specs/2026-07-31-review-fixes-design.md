# Review Fixes Design

**日期：** 2026-07-31
**分支：** `codex/review-fixes`
**基线：** `9451fc0`

## 目标与约束

本轮只处理代码审查确认的六类缺陷，并按规格、路径安全、API Key、上传收尾、平台生命周期、有限渲染、CI 产物校验的顺序交付。每个业务批次必须先用自动化测试复现缺陷，再做最小修复；每批单独验证、单独提交，便于逐提交复审和回退。

本轮不做无关重构，不改变现有 UI 信息架构，不引入虚拟列表库，不把移动 Playwright 加入主 CI，不推送或合并分支。真实 SillyTavern 连接、上传和热重载由用户在全部自动化验证后执行人工验收。

## 通用失败处理与验收

每批在开始时确认工作树只包含本批预期文件。聚焦测试必须先因目标行为缺失而失败，而不是因测试语法、环境或夹具错误失败。实现后依次运行聚焦测试、`pnpm test`、`pnpm typecheck`、`pnpm lint` 和 `git diff --check`；修改扩展源码或产物链路的批次还运行 `pnpm build:ext`。任何一步失败都停留在当前批次定位根因，不提交、不进入下一批。

构建扩展会更新根目录产物；这些产物属于对应批次并随批次提交。第 6 批的可重复构建检查以提交后的产物为基准，重建后要求 `index.js`、`bundle.js`、`style.css`、`version.json` 均无差异。

## 第 0 批：规格与实施计划

**解决的问题：** 把六类跨模块修复的行为、边界、失败语义和验证门槛固化，避免实现过程中扩大范围或混合提交。

**不修改的后果：** 复审者无法按批次判断目标是否达成，后续实现容易把生命周期、上传和图库性能混在同一补丁中。

**修改后的行为：** 本设计和实施计划成为每批测试、文件、提交和验收的共同依据。

**文件边界：** 只新增本文件与 `docs/superpowers/plans/2026-07-31-review-fixes.md`，不修改业务代码和生成产物。

**验收条件：** 两份文档完整覆盖第 1 至 6 批的问题、后果、期望行为、文件边界、失败处理、RED/GREEN 和验证命令，并作为独立提交。

## 第 1 批：变量路径安全

**解决的问题：** `setNested` 当前会沿 `__proto__`、`prototype`、`constructor` 等继承属性继续写入，攻击者可通过配置导入、设计器、AI Patch、手动编辑或 MVU 路径污染对象原型。

**不修改的后果：** 普通对象可能继承攻击者写入的字段，导致同页面其他扩展、判断逻辑和数据序列化出现跨对象污染。

**修改后的行为：** `splitPath` 统一拒绝危险路径段；读、写、删对危险路径均不产生效果。`状态.体力` 等正常点号路径保持现有语义。由于变量树会重导出路径工具，新变量引擎、运行时、设计器间接调用和 MVU 共用同一防线。

**文件边界：** 核心修改 `st-extension/src/apps/path-utils.ts`，新增或扩展同目录测试；只有测试证明上层入口未覆盖时，才在相应现有测试文件补集成断言，不复制第二套校验。

**失败处理：** 危险路径被视为无效路径：`getNested` 返回 `undefined`，`setNested` 和 `deleteNested` 静默不修改对象，兼容现有无返回值 API。

**验收条件：** 三个危险段在首段和中间段均被拒绝；`Object.prototype` 未出现污染字段；正常中文路径读写删除通过；上层共用路径的现有测试通过。

## 第 2 批：API Key 原子恢复

**解决的问题：** `fetchModels` 只在旧 Key 非空时恢复，并且恢复调用未 `await`；两个并发请求可交错写入临时 Key 和旧 Key。

**不修改的后果：** 查看模型列表可能永久改变用户当前 SillyTavern 密钥，或由较早请求的延迟恢复覆盖较晚请求正在使用的密钥。

**修改后的行为：** 模型发现操作进入模块级串行队列。每个操作独占“写临时 Key、请求模型、恢复旧 Key”的完整临界区；只要写过临时 Key，就在 `finally` 中恢复原值，包括空字符串，并等待恢复结束后才结算调用。

**文件边界：** 修改 `st-extension/src/apps/api/bridge.ts`，新增 `st-extension/src/apps/api/bridge.test.ts`。不改变站点档案格式、应用档案切换流程或 SillyTavern API 路径。

**失败处理：** 模型请求成功或失败都先尝试恢复。恢复失败不能被静默吞掉；若模型请求本身已失败，保留主错误并记录恢复失败上下文；若模型请求成功但恢复失败，则调用失败，避免向 UI 假装用户凭据已安全恢复。队列链在单次失败后仍可服务后续请求。

**验收条件：** 成功、HTTP 失败、空旧 Key、恢复等待和两次重叠请求全部通过；写 Key 的顺序严格为每个请求的临时值后跟原值，不交错。

## 第 3 批：上传流程收尾

**解决的问题：** 批量上传在绑定冲突或异常时可提前退出，绕过统一收尾；按钮仍可被重复触发，且导入成功后的渲染或提示异常可能把已落盘结果误报为上传失败。

**不修改的后果：** 窗口可能卡在处理中，同一批被重复执行，用户不知道成功、冲突、失败和未处理数量；已成功图片的真实状态与提示不一致。

**修改后的行为：** 单次上传由运行中守卫保护，所有出口经过同一 `try/finally`。批次累计成功、冲突、失败、未处理数量并展示总结。每张图片一旦通过 `updateSettings` 落盘即计为成功并保留；后续 UI 刷新或 toast 失败只能作为界面失败记录，不能改写落盘结果。

**文件边界：** 修改 `st-extension/src/sprite-manager.ts` 和 `st-extension/src/sprite-manager.test.ts`。不改变压缩、图床、本地保存、冲突判定或包拆分算法。

**失败处理：** 单张压缩、保存或图床异常按现有保底语义继续处理；会阻止继续导入的绑定冲突记录冲突和剩余未处理数，然后进入统一收尾。`finally` 恢复按钮状态并关闭预览遮罩，即使总结展示本身异常也不回滚数据。

**验收条件：** 重复点击只启动一次；成功、冲突、异常路径均退出运行中状态；总结四类数量准确；冲突前已落盘图片仍存在；落盘后的 render/toast 异常不产生“导入失败”误报。

## 第 4 批：平台生命周期

**解决的问题：** 同页再次执行 bundle 时，当前全局 disposer 只回收新变量运行时、手机壳和 capability tracker，未覆盖宿主订阅、楼层后处理、Prompt 主通道、overlay、manager、设置入口和动态 CSS。正常关闭 modal 后，其 close handle 仍可能留在 tracker 中。

**不修改的后果：** 热重载或重复执行会产生重复消息处理、重复角色处理、重复 DOM、陈旧闭包和残留 Prompt；tracker 长期持有已关闭 modal。

**修改后的行为：** `index.ts` 在创建新实例前调用旧实例 disposer，并用一个幂等清理聚合器登记所有顶层资源。各挂载函数返回或暴露最小 cleanup/destroy 契约。modal 仍是 mount 生命周期交接：内部资源只由 `build` 返回的 cleanup 管理；正常关闭时同时从平台 tracker 注销，平台销毁仍能关闭尚未关闭的 modal。

**文件边界：** 核心为 `st-extension/src/index.ts`、`core/app-modal.ts`、`core/phone-registry.ts`、`core/phone-shell.ts`、`st-extension/src/overlay-dom.ts`，以及现有 manager、settings、message-postprocess、adapter 中缺失 cleanup 契约的最小修改和对应测试。不新增 modal context，不重构 App 注册模型。

**失败处理：** 所有 cleanup 幂等；单项清理异常不得阻止其余资源回收。异步初始化在被新实例取代后不得重新挂载旧资源。定时的历史楼层重处理在 dispose 后不得执行。

**验收条件：** 第二次 bootstrap 前旧实例的消息/角色订阅、楼层后处理、Prompt、overlay、manager、手机壳、设置入口和动态 CSS 全部回收；DOM 无重复；已关闭 modal 不在 tracker 中；多次 dispose 不重复执行资源 cleanup。

## 第 5 批：千图包有限渲染

**解决的问题：** 详情页目前为包内所有图片一次性创建卡片和监听器，`loading="lazy"` 只推迟网络解码，不能降低 DOM、布局和事件成本。

**不修改的后果：** 1000 张图片的包会在打开详情页时创建上千卡片及其子节点，导致明显卡顿和内存增长，移动端更严重。

**修改后的行为：** 每次打开包详情只渲染前 60 张；“加载更多”每次最多增加 60 张，并显示 `已显示数/总数`。编辑后重渲染保留合理的已显示上限，切换包则重置为 60。灯箱的数据源仍为完整 `pack.sprites`，可浏览未渲染卡片对应的图片。

**文件边界：** 只修改 `st-extension/src/sprite-manager.ts`、`st-extension/src/sprite-manager.test.ts` 和必要的既有样式。不得引入虚拟列表依赖或重新设计管理页。

**失败处理：** 空包不显示加载控件；总数不足 60 时不显示“加载更多”；加载到末尾后移除控件。包在操作中缩短时，显示数钳制到新总数。

**验收条件：** 1000 张包初次 DOM 中 `.so-sprite-card` 不超过 60，计数为 `60/1000`；点击一次后不超过 120；末页不超总数；灯箱仍使用完整 1000 张集合。

## 第 6 批：CI 发布产物校验

**解决的问题：** CI 会构建扩展但不验证提交的根目录产物与源码一致；当前构建时间始终取本地当前分钟，使重建天然产生差异。

**不修改的后果：** 源码修改后即使遗漏 `bundle.js` 等产物，CI 仍可通过，用户安装的代码与审查过的源码不一致。

**修改后的行为：** `st-extension/build.mjs` 接受显式构建时间环境变量，严格验证 `YYYY-MM-DD HH:mm` 后再调用 esbuild 或写任何产物；未提供变量时保持当前本地时间行为。CI 从已提交 `version.json` 提取构建时间，固定时间重建，再用 Git 检查四个发布文件无差异。

**文件边界：** 修改 `st-extension/build.mjs`、`.github/workflows/ci.yml`，新增针对时间解析/预写失败的测试或可测试辅助模块，并更新四个根目录扩展产物。移动 Playwright 不加入该工作流。

**失败处理：** 缺省环境变量走本地时间；显式值格式或日期语义错误时，在 esbuild 和所有 `writeFileSync` 之前以非零状态退出，原产物字节不变。`version.json` 不符合版本格式时 CI 立即失败。

**验收条件：** 相同源码与固定时间连续构建字节一致；错误时间不改写任何产物；不指定时间仍生成当前本地分钟；CI 固定时间重建后四个文件 `git diff --exit-code` 通过。

## 提交顺序

1. `docs: plan review fix batches`
2. `fix: reject unsafe variable paths`
3. `fix: restore temporary API keys atomically`
4. `fix: finalize interrupted sprite uploads`
5. `fix: dispose extension resources on reload`
6. `perf: bound sprite gallery rendering`
7. `ci: verify committed extension artifacts`
