# STS UX and Performance Design

> Status: proposed for the 2026-08-07 maintenance batch

## Intent

Make the first use of the Renderer understandable to a new SillyTavern user, make the ST installable output an explicit build product, and preserve a low-cost path for a later remote sprite catalog. The current reference image set is an input to that later catalog, not a bundle dependency for this batch.

## Scope

### Near-term delivery

1. Improve the Renderer App onboarding surface.
2. Add a deterministic optional ST distribution export target without maintaining a second hand-copied source tree.
3. Add tests for the new user-facing states and export boundary.
4. Document the resource boundary and explicitly defer the uncleaned reference images.

### Deliberately deferred

- Removing baked checkerboards from the 143 reference PNGs.
- Uploading assets to a specific image host or CDN.
- Automatic remote catalog synchronization.
- Browser/server local-download storage implementation.
- Replacing existing root build artifacts or changing the product semantic version.

## UX Design

The Renderer App remains a settings App. Its first section becomes a compact onboarding panel with four pieces:

- **Current state**: a truthful status derived only from persisted Renderer settings: disabled, enabled with the selected modes, or enabled with no modes.
- **Quick start**: three steps: enable Renderer, leave at least one mode enabled, then send a normal message. The prompt is injected through the existing App channel; the user does not need to manually paste JSON.
- **Mode guide**: Galgame is for dialogue/scene beats, card choice is for 2-8 choices and inserts a draft without auto-sending, and battle is for local deterministic actions.
- **Troubleshooting**: the Renderer appears only when the model returns a valid `<STStageRender>...</STStageRender>` block. If a normal reply has no block, the original prose remains unchanged. The guide points the user to enable the setting before sending the next message and to verify the build stamp in the ST extension panel.

The panel gets one explicit `启用推荐设置` action when disabled. It sets only `enabled: true` and leaves all mode and behavior preferences unchanged. This avoids silently changing a user's mode choices. The status must never claim that the current model supports rendering or that a message was rendered; it reports configuration only.

Details are implemented with existing native DOM helpers (`section`, `foldSection`, `appButton`, and `so-app-desc`) and the existing `renderer-settings` class prefix. No new framework or persistent schema is needed. Existing control labels, defaults, prompt injection, and reprocess behavior remain unchanged.

## ST Distribution Boundary

`st-extension/` is the source integration directory. The repository root remains the current compatibility output consumed by the existing GitHub/ST installation flow. A new `st-distribution/` directory is an explicit generated export target, not a second source tree.

The export contains:

- `manifest.json` copied from the source root;
- `index.js`, `bundle.js`, `style.css`, and `version.json` generated by the existing build;
- a short README describing the generated-only contract.

The default `build:ext` path continues to write the root artifacts. A separate `build:st` command writes `st-distribution/` using the same `buildExtension` function and the same fixed build-time input. No reference images or simulator-only `public/` assets are copied into the export by default. This makes the future standalone repository a clean extraction of a known output rather than a manually synchronized folder.

## Future Sprite Catalog Contract

When a host is selected, the catalog should expose stable records independent of filenames:

```ts
interface RemoteSpriteCatalogEntry {
  id: string
  role: string
  outfit: string
  tag: string
  url: string
  previewUrl?: string
  sha256: string
  width: number
  height: number
  format: 'webp' | 'png' | 'avif'
}
```

The runtime should use HTTPS URLs by default, keep settings small, and offer the existing manual localization path as the explicit local/server download action. Catalog generation must reject baked-checkerboard candidates unless they are marked as ordinary background images. The current PNGs need a separate cleanup/quality gate before entering this contract.

## Error Handling

- Missing or malformed App data continues through `normalizeRendererSettings`.
- Enabling with no mode shows a warning state and does not inject a prompt.
- The export command fails before writing artifacts if the source manifest or output setup is invalid.
- Existing runtime parse failures continue to fall back to original message prose.
- The onboarding copy uses `textContent`; no user or model text is inserted as HTML.

## Verification

- Unit tests cover disabled, enabled, no-mode, and recommendation-action states in `renderer-app.test.ts`.
- Build tests cover a distinct output root containing the copied manifest and generated artifacts, plus the absence of simulator/reference image copies.
- Typecheck, lint, focused Vitest, deterministic extension build, artifact diff, and the existing mobile E2E suite remain the verification gates.
- Real ST acceptance still requires a human check of the new guide, cache stamp, prompt injection, and all three Renderer interaction paths.
