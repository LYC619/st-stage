# 语义短地址与大图包策略设计（草案）

日期：2026-07-25  
状态：已通过 Claude Code v2 复审并吸收最终意见，进入实施计划阶段

## 1. 决策摘要

当前“多包始终输出 `<名称>@<p|r>=<完整 ID>`”方案，虽然能把地址绑定到物理图包，但会把完整包 ID 重复写入每一张图片地址。图数从几十张扩大到上千张时，Prompt 成本按“图片数 × ID 长度”增长；这笔成本由所有用户承担，而真正同时启用同名、同角色、同表情且内容不同的包是低概率情况。

本方案改为：

1. 地址表达“当前启用集合中的语义角色/服装/表情”，不表达历史物理包身份。
2. 在导入、合并和启用边界阻止会产生歧义的有效地址；允许已安装但未同时启用的同名/不同风格包共存。
3. Prompt 只使用干净的语义地址，例如 `鸣人/微笑`，不再生成 `@p=`、`@r=` 或完整 ID。
4. 解析器保留跨包多解返回 `null` 的防线，防止手改设置或旧脏数据造成误配。
5. 大图包使用按场景分组的 Prompt；`repeat` 模式用“共有表情 + 各场景增量”压缩，避免每张图片重复角色名。
6. 图包是安装/分发单位，启用集合才是 Prompt 单位；不活跃的系列图包不应进入当前角色的 Prompt，也不应被全部预加载。

项目主要展示最近几楼的聊天，因此本方案不把“切换图包后主动重绘旧楼层”列为产品能力。绑定变更只保证后续新消息和当前悬浮窗使用新的启用集合；既有 inline 楼层不主动重处理，直到用户执行其他正常刷新流程为止。历史楼层与物理图包之间不建立永久绑定。

## 2. 目标与非目标

### 目标

- 让普通多包 Prompt 使用短语义地址，去除逐图重复的包 ID。
- 在用户创建/导入/启用包时尽早发现地址冲突，并给出可理解的修复动作。
- 保持不同服装、不同表情集合可以组合启用；只阻止真正相同的最终地址指向不同图片。
- 让一个包含数百或上千张图的系列可以按角色、分组和共享表情压缩注入。
- 让大包安装不会自动造成全量图片网络预加载。
- 对绕过 UI 的旧设置保持失败安全：冲突地址不静默选择第一个包。
- 不为图包绑定变更增加全楼层 fingerprint 或主动重处理链路。

### 非目标

- 不为聊天历史保存物理图包 ID 或永久别名映射。
- 不保证当前未发布的 `@p=` / `@r=` 实验地址永久兼容；本轮 canonical 方案尚未发布。
- 不在本轮实现通用向量检索、按语义自动选择未列入 Prompt 的图片。
- 不把一个系列的所有图片强制塞进每个角色的活动集合。

## 3. 地址语义模型

### 3.1 有效坐标

每张图片先计算有效坐标。必须先得到有效服装，再决定是否需要包名 fallback：

- `outfit = sprite.outfit || pack.outfit`
- `role = sprite.group || pack.roleName || ((multiPack || outfit) ? pack.name : '')`
- `tag = sprite.tag`

空值按空串处理，比较前使用现有命名清洗/trim 规则。显示格式仍为：

- 无角色：`微笑`
- 有角色：`鸣人/微笑`
- 有角色和服装：`鸣人/居家服/微笑`

两段地址 `角色/表情` 明确表示 outfit 为空；解析时不得回落到任意有服装的同名图片。有服装的图片必须使用三级地址。单包若没有 `roleName/group` 但存在 outfit，也使用包名作为 role，生成 `包名/服装/表情`，避免服装维度在格式化时丢失。

同一包内的 `group`/`roleName` 继承仍由现有 CRUD 有效地址规则统一处理。

### 3.2 绑定变更的生效范围

- 新收到的 AI 消息、当前悬浮窗和任何显式触发的正常解析都使用当前角色当前启用的包集合。
- 绑定变更不触发全楼层 inline 重处理，不修改消息处理 fingerprint，也不要求既有 DOM 立绘立即切换。
- 用户之后重新加载聊天或主动触发既有刷新流程时，若平台重新解析原始标签，解析结果自然以当时的启用集合为准；这属于现有刷新行为，不是本功能的稳定性承诺。
- 目标是降低寻址与维护复杂度，不保证历史消息固定到原物理图包，也不保证切换后立即重绘历史楼层。

## 4. 地址唯一性策略

### 4.1 冲突键

对一个角色的候选包集合计算：

```text
conflictKey = JSON.stringify([effectiveRole, effectiveOutfit, tag])
```

检测器必须以**操作成功后拟生效的完整包集合**为输入，再根据该最终集合的长度计算 `multiPack`，并重新计算集合内所有包的有效坐标。不能沿用操作前的单包坐标，否则“追加第二个包”会漏掉或误报 fallback role 冲突。

只有以下情况算启用冲突：

- 同一个 `conflictKey` 出现在两个不同包时，默认视为冲突（即使当前 URL 恰好相同）；合并流程可以把相同 URL 识别为重复项，但运行时不保留两个所有者。

以下情况允许同时启用：

- 同角色但表情集合不重叠；
- 同角色但服装不同；
- 包名不同但最终有效角色、服装、表情不冲突；
- 同一包内部的历史重复项（由 `upsertSprite`/数据清理处理，不扩大跨包冲突）。

包名相同本身不是硬冲突；但包名是无语义图片的 fallback role，因此若最终地址重复，仍会被冲突检查捕获。`pack.roleName` 与其他包的 `sprite.group` 也使用同一套有效坐标比较。

### 4.2 检查边界

冲突检查不能只放在 `importPack()`：该函数没有当前角色和已启用集合上下文。应提供纯函数级检查，并由所有改变绑定的入口调用：

- 导入/解码分享串完成后，展示与现有包的名称、角色和有效地址重叠摘要；
- `bindPack` / `setBinding` 启用新包前检查目标角色的完整集合；
- `toggleBinding(enabled=true)` 重新启用整组绑定前也必须检查；`bindCharacter` 委托给 `setBinding`，不需要另建规则；
- `upsertPack` 覆盖一个已被启用绑定引用的包时，必须对所有受影响角色的最终集合重新检查；上传、改名、改分组、改服装或包级元数据不能借由“绑定没变化”绕过唯一性约束。新增但尚未绑定的导入包不产生活动冲突，可直接安装；
- 批量绑定或切换画风时一次性检查，避免逐项操作产生半完成状态；
- 加载手改/历史设置时不强制抛错，但生成冲突诊断，运行时按失败安全规则处理。

校验必须由核心绑定变更函数自身执行，不能只依赖 UI 预检；UI 预检用于提前展示冲突和可选动作，核心函数负责最终强制。绑定变更使用确定的判别联合返回值：

```ts
type BindingChangeResult =
  | { ok: true; settings: PluginSettings }
  | { ok: false; conflicts: BindingConflict[] }
```

`upsertPack` 使用同形的 `PackChangeResult`，并在冲突项中附带受影响的 `characterName`；双端调用方只在 `ok:true` 时持久化。低层迁移/加载可以构造历史脏设置，但正常编辑路径不能借此产生新的活动冲突。

`BindingConflict` 至少包含结构化地址、格式化完整地址，以及每个冲突所有者的包 ID、包显示名、图片 URL。失败分支不产生部分设置，也不返回一个可误提交的“半完成 settings”；调用方保留原 settings 并根据 conflicts 展示动作。

`toggleBinding(enabled=false)` 永远允许。`toggleBinding(enabled=true)` 与新增绑定使用同一硬校验：若既有绑定集合含冲突，则返回 `{ ok:false }` 且保持关闭。关闭状态下仍允许逐包解绑、替换或合并，因此不会锁死用户；若历史/手改设置在加载时已经处于“启用且冲突”状态，则不追溯抛错，由 Prompt 排除歧义地址、解析器返回 `null` 并展示诊断。

### 4.3 用户动作

导入同名或重叠包时提供：

1. **合并**：创建一个新的合并结果或明确写回目标包；按有效坐标去重，URL 不同的同址图片逐项询问保留目标/保留导入/跳过。
2. **重命名后安装**：包名只解决 fallback role；若冲突来自 `roleName/group`，需要在预览中提示编辑角色/分组，而不是假装改包名即可解决。
3. **仅安装不启用**：包保留在图库中，当前角色不绑定它。
4. **取消**。

启用冲突包时优先提供“替换当前冲突包”（适合切换画风）、“合并后启用”和“取消”。不静默追加，也不自动把用户不熟悉的名字改成 `鸣人2`。

合并时若两个包的包级 `roleName/outfit` 不一致，应先把每张图片的有效 role/outfit 实体化，再选择新的包级默认值；不能简单覆盖包级字段导致地址漂移。

### 4.4 单包到多包的 fallback 变化

无 `roleName/group` 的包在单包时可以使用纯图名（如 `微笑`）；当第二个包被启用后，该包会使用包名 fallback（如 `鸣人包/微笑`）。这是现有短地址兼容规则的必要变化：新增包可能使旧的纯图名变成多解，解析器按防线返回 `null`，不尝试猜测归属。

绑定 UI 应在“追加第二个包”前预览受影响的地址和可能失效的裸标签；本方案不为此增加历史别名或旧楼层重处理机制。若用户希望保持旧地址可用，应合并包、补充 roleName/group，或只启用一个包。

## 5. 解析器行为

### 5.1 正常路径

- `flatten()` 生成干净的有效 role/outfit/tag，不再生成 canonical token。
- 精确匹配优先；角色、服装、图名各层锁定后再进入下一层。
- `角色/表情` 只在空 outfit 候选中匹配；不存在空 outfit 时返回 `null`，不回落到某个服装。
- 当前启用集合中同一地址只有一个候选时返回该图片。

### 5.2 防线

- 跨不同包的同地址多解：返回 `null`，绝不按绑定顺序选第一个。
- 同一包内部历史上多个分组共用纯图名：保留既有首项兼容行为；带角色/服装的地址仍按对应维度解析。
- 模糊匹配跨包多解：返回 `null`。
- 目标包未启用、角色/服装不存在：返回 `null`，不回落到其他包。
- 未发布的 `@p=` / `@r=` 地址不列为兼容承诺；若保留临时识别代码，也必须独立于正常 Prompt 生成路径，并在文档中标明可移除。

上游冲突检查是常规数据入口的约束，但不是唯一安全边界；任何绕过 UI 的设置、迁移或手工 JSON 都必须仍由解析器的跨包多解 `null` 规则兜底。该不变式不可因“理论上 UI 已拦截”而删除。

## 6. 大图包 Prompt 策略

Prompt 压缩的前提是不变式：当前活动集合中每个最终 `role + outfit + tag` 至多对应一个包。冲突检查失败或脏数据导致的多解地址不得被 Prompt 伪装成一个可用候选；应从可用列表中排除并报告诊断。Prompt builder 不负责决定所有权，也不生成新的别名。

### 6.1 `full`：按场景分组的精确枚举

`full` 不再逐行重复角色前缀，改为：

```text
可用立绘：
- 鸣人：微笑、生气、害羞
- 鸣人/居家服：微笑、睡觉
- 佐助：微笑、冷漠
```

这与逐条地址等价，但角色/服装只出现一次。空服装场景与具体服装场景是不同分组；例如 `鸣人：微笑` 只还原为 `鸣人/微笑`，不会命中 `鸣人/居家服/微笑`。Prompt 明确说明生成格式仍为 `[立绘:场景/表情]`，不存在的组合不可自行拼造。

### 6.2 `repeat`：共有集合 + 场景增量

对每个场景（role/outfit）建立 tag 集合：

```text
可用场景：鸣人、鸣人/居家服、佐助
共有表情：微笑
各场景其余表情：
- 鸣人：生气、害羞
- 鸣人/居家服：睡觉
- 佐助：冷漠
```

共有集合取所有场景的交集，非共有项按场景分组列入“该场景其余表情”；“其余”不表示只属于一个场景，同一非共有 tag 可以出现在多个场景列表中。Prompt 必须明确写出“共有表情适用于全部已列场景，各场景其余表情只按所在行使用”。不再把每个增量写成重复的 `角色/表情` 字符串。若交集为空，退化为 6.1 的分组精确枚举。

`repeat` 应在“共享格式”和“分组精确格式”之间选择较短且仍完整的结果，避免交集很小时反而增加说明文字。比较双方最终完整 Prompt（包含说明和输出约束）的 UTF-16 `string.length`；若长度相同，选择分组精确格式（说明更直接）。两种格式都必须能还原实际存在的 role/outfit/tag 组合。

### 6.3 新用户默认与现有设置

- 保留现有 `full` / `repeat` 设置值，避免破坏旧用户偏好。
- 新安装默认建议改为 `repeat`；已有保存为 `full` 的用户不强制切换。
- 不做静默截断。若完整地址本身超过上下文预算，应在 Prompt 预览或配置面板显示长度警告，并建议拆包/减少活动集合/规范化 tag。

### 6.4 大系列的作者规范

一个“原神系列”应优先按运行时角色拆成多个包，或由一个安装清单一次安装多个角色包；不要把所有角色都绑定到每个聊天角色。若确实使用单个多角色包，应通过 `sprite.group` 提供角色层，并确保 tag 词表尽量统一。

例如 50 个角色各有 20 个共同表情时，`repeat` 只需枚举约 50 个角色名和 20 个表情名，而不是重复 1000 个完整地址。若 1000 个 tag 全部独特，则无法在不提供这些名称的前提下让模型可靠选择；此时应拆包或引入未来的检索机制，而不是再压缩 ID。

## 7. 安装、存储与运行时性能

### 7.1 安装与分发

当前 `SpritePack` 仍是运行时包单位。系列分发可在后续增加 `sprite-collection@1` 清单，一次安装多个子包，但安装不等于绑定；这不应把所有子包自动加入当前 Prompt。

大图包的图片优先使用静态/远程 URL 或可按需读取的资源，不把大量图片全部嵌入设置 JSON。导入预览只读取元数据和冲突摘要，用户确认后再完成图片迁移。

### 7.2 预加载

当前 `preloadPack()` 会遍历活动包的全部图片。大包策略应改为：

- 初次激活只加载绑定顺序中前几张封面/首图，设置全局上限 `PRELOAD_ON_ACTIVATE_MAX = 4`；
- 收到 AI 标签后只预加载本次解析出的图片序列，最多 `PRELOAD_MATCH_MAX = 10` 张；
- 对下一张轮播图只在上述总上限内做有界预加载；
- 不因 Prompt 枚举而创建上千个 `Image` 对象。

上述 4/10 只限制通过 `new Image()` 主动预加载的悬浮窗路径。inline 楼层在实际渲染时创建真实 `<img>`，由现有 `recentFloors` 楼层窗口独立有界，不占用也不扩张主动 preload 预算。命中序列超过 10 张时，第 11 张及以后只在轮播实际切换到该图片时按浏览器正常图片加载，不额外预取。

图库 UI 对大量图片使用分页、虚拟列表或 `loading="lazy"`，避免安装一个系列就渲染全部缩略图。

## 8. 迁移与发布边界

- 当前 `@p=` / `@r=` 方案尚未发布、尚未提交；回退到语义短地址不需要为真实用户保留物理 ID 映射。
- `PluginSettings` 版本可维持现有版本，除非新增系列清单或新的 Prompt 模式字段。
- 现有 `multiRolePromptMode` 继续支持 `full` / `repeat`；分组输出属于实现改进，不改变配置值含义。
- 测试期间产生的 canonical 文本不作为正式兼容承诺；若产品希望兼容，需另开迁移任务，不能半保留半删除。
- 不新增消息 fingerprint 字段，也不因 `packs/bindings` 变化主动调用全楼层重处理。

## 9. 测试矩阵

### 地址与冲突

- 同包多角色、包级 roleName、sprite.group、包名 fallback 的有效坐标一致性；
- 同角色不同服装允许共存；同角色不同 tag 集合允许共存；
- 包名与另一包 roleName/group 相同但最终 tag 不重叠时允许共存；
- 完整 role/outfit/tag 相同的不同包被拒绝，冲突报告包含双方包和图片；
- `setBinding`/`bindPack`/`bindCharacter`/`toggleBinding(enabled=true)` 返回 `BindingChangeResult`；`upsertPack` 返回同形的 `PackChangeResult`；冲突时为 `{ok:false}` 且原 settings 不发生部分修改，替换/取消动作结果正确；
- 向已启用包上传、改名、改分组、改 outfit 或修改包级 role/outfit 后若产生跨包同址，`upsertPack` 必须拒绝；未绑定的新导入包仍可安装；
- `toggleBinding(enabled=false)` 永远成功；冲突集合重新开启失败后仍可逐包解绑并恢复；
- 手改冲突设置时 Prompt 不枚举不可解析地址，解析跨包多解返回 `null`；
- 新消息和当前悬浮窗使用当前启用集合；绑定变更不要求既有 inline 楼层立即重绘；
- 单包追加第二包时，fallback role 的地址变化和裸标签多解均有明确测试；
- 同一 role 的空 outfit 与具体 outfit 存在同名 tag 时，`role/tag` 只命中空 outfit，三级地址命中对应服装；单包无 role 但有 outfit 时使用包名形成可逆三级地址；
- 不再生成 `@p=` / `@r=`，也不依赖 `encodePackId`。

### Prompt

- `full` 输出按 role/outfit 分组，地址组合完整且不重复角色前缀；
- `repeat` 正确输出共有 tag 与各场景增量，不生成不存在的组合；
- 交集为空时退化为完整分组；
- 50 角色 × 20 共同 tag 的模拟数据中，Prompt 不重复每个 canonical ID，长度显著低于旧方案；
- 1000 条地址仍能在合理时间内构建，且不遗漏实际组合；
- 单包纯图名、三级地址和旧签名测试无回归。

### 性能与导入

- 激活大包时创建的 `Image` 数量不超过 `PRELOAD_ON_ACTIVATE_MAX`；收到标签后不超过 `PRELOAD_MATCH_MAX`；
- 导入同名/重叠包的合并预览不修改原包；
- 合并时包级继承字段实体化后地址不漂移；
- 大量缩略图使用 lazy/分页策略。

## 11. 验收标准

1. 普通多包 Prompt 中不再出现完整包 ID 或 `@p=`/`@r=`。
2. 新消息和当前悬浮窗使用当前启用包；历史 inline 楼层不要求因绑定变化立即重绘。
3. 真正冲突的启用操作在变更前被拦截，并给出可执行的替换/合并/取消选项。
4. 非冲突的不同服装或不重叠表情集合可以组合启用。
5. `full`/`repeat` 对大角色集合的 Prompt 不重复逐图包身份，且不伪造不存在的组合。
6. 冲突脏数据不会跨包误配；解析多解返回 `null`。
7. 大包激活不会全量预加载所有图片。
8. 全套 Vitest、TypeScript、ESLint、扩展构建和 Next 构建通过。

其中第 3 项必须由核心绑定 API 强制执行；只在某个 UI 入口显示警告不算通过。

## 12. Claude Code 审查重点

请重点审查：

- 冲突检查是否覆盖 `pack.name` fallback、`roleName`、`sprite.group`、`outfit` 的交叉命名空间，并严格使用变更后的最终集合计算 multiPack；
- 绑定及活动包内容变更的冲突失败是否原子、是否可能通过 `upsertPack`、上传或元数据编辑等入口绕过；
- 绑定变化是否错误地触发或依赖全楼层重处理；历史 inline 楼层保持“无主动换肤保证”的边界；
- `BindingChangeResult` 是否在 core/Web/ST 调用方一致处理；`toggleBinding(enabled=true)` 是否硬阻止冲突而关闭/解绑仍可恢复；单包追加第二包时 fallback role 变化是否有预览和安全 null；
- 两段 `role/tag` 是否只解析空 outfit，单包 outfit 是否始终生成可逆的三级地址；
- `repeat` 的共有+增量格式是否仍能让模型构造合法地址；
- “较短”是否按 UTF-16 `string.length` 确定性比较并有平局规则；
- 单个系列包与多个角色子包的 Prompt/预加载边界；
- 预加载上限是否严格为 4（激活）/10（命中序列）；
- 合并包时包级继承字段是否会造成地址漂移或重复；
- 是否存在必须保留的已发布 canonical 数据（若没有，应删除所有实验兼容代码）。
